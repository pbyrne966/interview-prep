  CRESTA FEATURE SPEC — Build This Feature
  Conversation Silence Detector & Alert System
============================================================

------------------------------------------------------------
BACKGROUND
------------------------------------------------------------
Cresta's platform monitors live contact-centre conversations
in real time. One quality signal that matters to supervisors
is "dead air" — stretches of silence where neither the agent
nor the customer is speaking. Long silences often indicate:

  • The agent is confused and searching for an answer
  • The customer is on hold without being told so
  • A technical issue on the call

This feature asks you to build a system that ingests a
stream of timestamped conversation events and fires an alert
whenever silence exceeds a configurable threshold.

------------------------------------------------------------
WHAT YOU NEED TO BUILD
------------------------------------------------------------
A class called ConversationMonitor.

    class ConversationMonitor:
        def __init__(self, silence_threshold_seconds: int) -> None
        def record_event(self, conversation_id: str, timestamp: int) -> list[dict]

Each call to record_event() represents a speech event — either
party said something at that timestamp for that conversation.

record_event() must return a list of ALERT dicts. Most of the
time this list will be empty. An alert is emitted when the gap
between the current event and the PREVIOUS event for that
conversation_id exceeds silence_threshold_seconds.

Each alert dict must have this shape:
    {
        "conversation_id": str,
        "silence_start":   int,   # timestamp of the last event before the gap
        "silence_end":     int,   # timestamp of the current (new) event
        "duration":        int,   # silence_end - silence_start
    }

------------------------------------------------------------
RULES & EDGE CASES TO THINK ABOUT
------------------------------------------------------------
1.  First event for a conversation never triggers an alert
    (there is no "previous" timestamp to compare against).

2.  Multiple conversations must be tracked independently.
    An event in conversation "A" must not affect "B".

3.  If TWO events arrive at the exact same timestamp for
    the same conversation, duration = 0, so no alert fires
    (0 does not exceed the threshold).

4.  Events are NOT guaranteed to arrive in order across
    conversations, but within a single conversation_id
    assume they arrive in non-decreasing timestamp order.

5.  You may receive many events per second per conversation.
    The solution should be O(1) per record_event() call.

6.  The threshold is STRICTLY greater than — a gap of exactly
    silence_threshold_seconds does NOT trigger an alert.
    Only gaps > threshold trigger.

------------------------------------------------------------
EXAMPLE WALKTHROUGH
------------------------------------------------------------
monitor = ConversationMonitor(silence_threshold_seconds=5)

monitor.record_event("conv-1", 0)    →  []   # first event, no alert
monitor.record_event("conv-1", 3)    →  []   # gap = 3, not > 5
monitor.record_event("conv-1", 10)   →  [    # gap = 7, exceeds threshold!
    {
        "conversation_id": "conv-1",
        "silence_start":   3,
        "silence_end":     10,
        "duration":        7,
    }
]
monitor.record_event("conv-2", 0)    →  []   # different conversation, first event
monitor.record_event("conv-1", 12)   →  []   # gap = 2, not > 5
monitor.record_event("conv-2", 100)  →  [    # conv-2 gap = 100, exceeds threshold!
    {
        "conversation_id": "conv-2",
        "silence_start":   0,
        "silence_end":     100,
        "duration":        100,
    }
]

EXTENSION (if you finish early — good talking point)
------------------------------------------------------------
Add a method:

    def get_stats(self, conversation_id: str) -> dict | None

Returns None if the conversation_id has never been seen.
Otherwise returns:
    {
        "total_events":       int,
        "total_alerts_fired": int,
        "longest_silence":    int,
        "last_event_time":    int,
    }

This mirrors the kind of real-time analytics Cresta actually
surfaces to supervisors in their dashboard.

------------------------------------------------------------
SUGGESTED APPROACH
------------------------------------------------------------
  Data structure:
    self.last_seen: dict[str, int]
      → maps conversation_id to the timestamp of the most
        recent event received.

  On each record_event():
    1. Look up last_seen[conversation_id].
    2. If not present: store timestamp, return [].
    3. Compute gap = timestamp - last_seen[conversation_id].
    4. Update last_seen[conversation_id] = timestamp.
    5. If gap > threshold: build and return the alert dict.
    6. Otherwise return [].

  This is deliberately simple so that in an interview you can
  implement it quickly and spend your time talking about:
    • What happens if events can arrive out of order?
    • How would you persist this state (Redis, Postgres)?
    • How would you scale this to 10,000 concurrent convos?
    • How would you replay historical events for a back-fill?
